# 超级猪咪样板总成 —— 账实核对与上游对照（2026-11-25）

> 触发：队长报「超级样板总成不吃单（样板自带编程电路 / 虚拟原料的不消耗物品都不接受），完全 IDLE」，要求「调查分析超级样板总成，对照着看看」。

## 1. 四台对照（同一件事在四个实现里长什么样）

| 项 | 普通猪咪 MV~UIV（10 台） | **超级猪咪**（本模组） | gtladditions 超级样板总成（上游） | gtlcore 原生 ME 样板总成 |
|---|---|---|---|---|
| 方块 id | `gtlmodular:<tier>_me_pattern_assembly` | `gtlmodular:super_me_pattern_assembly` | `gtladditions:me_super_pattern_buffer` | `gtceu:me_pattern_buffer` |
| 实现类 | `MoltenPatternAssemblyPartMachine` | **同一个类** | `MESuperPatternBufferPartMachine` | `MEPatternBufferPartMachine` |
| 继承 | gtlcore **具体类** `MEPatternBufferPartMachine` | 同左 | 同左（+ `IWidePatternBuffer`） | — |
| 槽数 | `pagesForTier(tier) × CAPACITY_PER_PAGE(128)`，最高 5×128=**640** | `MAX_PAGES(5) × PER_PAGE(160)` = **800** | 构造参数 `patternsPerRow(9) × rowsPerPage(6) × maxPages(3)` = **162** | 由注册处给 |
| tier | MV=2 … UIV=11 | **10（UEV）** | — | — |
| 存储 | gtlcore 的 `itemInventory/fluidInventory`（long） | 同左 | **自造 `Int128` 宽表 `inputs`** + `pending` 输出池，`itemInventory` 恒空 | gtlcore 原版 |
| 配方/催化剂匹配 | gtlcore `handleItemInternal` | 同左 | **整套重写**（`handleItemInternal`/`isActive`/`getItemInventory` 全部走自己的宽表） | gtlcore 原版 |
| 输出 | gtlcore `buffer` + `Ticker` | 同左 | 自造 `pending` + 自己的 `Ticker` | gtlcore 原版 |
| 神锻 FOA | 我们自己的 `isFoaRewriteActive`/`rewriteFoaPattern` | 同左 | `getRealPattern` 里 `rewriteForgeOfTheAntichristPattern` | 无 |
| 专属催化剂槽 / 归档 / 自动命名 / 自动切模式 / 逐槽模式 | 有 | **有（同一份代码）** | 部分 | 无 |

**结论一：我们的「超级」不是另一种机器，就是普通猪咪把槽数放大**（注册处 javadoc 原文也是这么写的：
"功能与普通猪咪样板总成完全一样，只是槽位更多"）。它没有任何「超级专属」的代码路径 ——
唯一的差别是构造参数 `maxPatternCount`。上游 gtladditions 的超级确实是另一套实现（Int128 宽表 +
自己的一套匹配/输出），但那套我们**没有搬**，也不在本模组的功能承诺里。

⇒ **推论（可直接验证）**：既然类相同、代码路径相同，**同一个 bug 不可能只出现在超级上**。
请把同一张样板放进任意一台普通猪咪（如 UV 档）复看：若那边也不吃单 ⇒ 属 Molten 共用路径的
问题（与超级无关）；若那边正常，问题才可能在 `maxPatternCount=800` 这一处。

## 2. 账实不符（本次订正）

1. **槽位数量：实机 800，文档/提示写 640**
   - 代码：`slots = SUPER_PATTERN_ASSEMBLY_PAGES(MAX_PAGES=5) × PER_PAGE(160)` = 800；
     注册日志一直打的是 `样板槽=800`。
   - 文档：旧 javadoc 写「UIV 级、5 页（每页 128）= 640 槽」；`zh_cn.json` 的
     `super_pattern_assembly.tooltip.1` 写「640 个（最多 4 页 × 每页 160 格）」。
   - 根因是**两套页单位被混用**：普通档容量按 `CAPACITY_PER_PAGE = 128`（历史存档口径，铁律不可改），
     而界面按 `PER_PAGE = 160`（16 列 × 10 行）。超级档的表达式用了「容量页数 × 界面每页格数」。
   - **决定：不缩容**（仓库铁律「绝不缩容」）：现役存档可能已有槽位号 ≥ 640 的样板，
     缩到 640 会直接抹掉。→ 只订正文档与工具提示，容量保持 800。
     真要让两档口径统一，正确方向是**把普通档放大**，绝不是把超级档缩小。
2. **tier：实机 10（UEV），文档写 UIV**
   - `SUPER_PATTERN_ASSEMBLY_TIER = 10`（GTValues.UEV）；普通档 UIV 是 tier 11。
   - 影响面：外壳档位贴图、按 tier 做的任何判定（`pagesForTier(10)` 已封顶 5 页，故不影响槽数）。
   - 只订正注释，**不改 tier**（改档位等于换外壳外观，且可能与玩家既有的贴图预期冲突）。
3. **没有超级专属机制**（见上表）：不是缺陷，是设计；记在这里免得后来者以为漏搬了什么。

## 3. 本次一并落地的其它两处（不属超级专属，但同一条链）

- 0.3.488 惰性机：样板自带电路 → 槽级电路缓存（**玩家拿不到惰性机，此条为代码一致性**）。
- 0.3.489 现役/超级机：读档补齐槽级电路缓存（`SlotCacheManager` 不落盘 `circuitCache`，
  读档后任何要电路的配方都会在 gtlcore 的模拟闸门 `leftCircuit != circuitCache` 被判「原料不足」）。

## 4. 仍未定案的现场判据

现役实例 `config/gtlmodular-common.toml` 里是 `identityGate = false`、`debugLogs = false`
⇒ 所有拒绝路径都是**静默**的，「什么提示都没有」不能当作「链路正常」的证据。

下一步只需一条读数，二选一：
- 换上 0.3.489+ 后进世界，日志里搜 `读档补齐槽级电路缓存`：出现「恢复 N 个槽」且机器开跑 ⇒ 定案。
- 若 N=0 仍 IDLE：把 `debugLogs` 改 `true` 跑一轮，日志会写出 `跨表` / `强匹配` 这类拒绝原因
  （`MoltenPatternAssemblyPartMachine#logGateReject`），照它改即可。
