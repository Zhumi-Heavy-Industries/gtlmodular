# 夹具脚本约定（`src/gametest/*/kubejs`）

这些脚本跑在两套最小依赖测试服里（见 [测试.md](测试.md)），不打进发行 jar，但**它们是 GameTest 的输入**：写错了不是"少几条配方"，而是数据包解析期报错、整套夹具连带失败。下面这几条是踩出来的，不是偏好。

## 一、命名：一份阶段一份职责

| 目录 | 用途 | 命名 |
|---|---|---|
| `startup_scripts/` | 注册 `kubejs:*` 测试物品、写 `global` 共享清单 | `*.items.js`；跨阶段共享清单用描述性名字（`nac_calibration.js`），**不要再有同名文件** |
| `server_scripts/` | 生成测试配方（数据包或构建器） | `*.recipes.js`（例外：与校准共用的清单生成器保留 `nac_calibration_tiers.recipes.js` 这种带场景名的写法） |
| 启动探针 | 只为给 Java 侧一个"startup 跑到了"的可观测点 | `probe_startup.js` |

**同名成对必须加后缀**：以前 `nac_matrix_tier.js` 这类文件在 startup 与 server 各有一份（本批已改成 `*.items.js` / `*.recipes.js`），改的时候分不清改的是物品还是配方——件数表漏改一侧曾经把测试服搞崩过一次，这是同形风险。后缀让"我改的是物品还是配方"一眼可见。改名不影响加载——KubeJS 按目录阶段加载，Java 侧不按文件名引用任何脚本。

## 二、什么算"依赖某个模组"

看正文里实际出现的东西，不要凭文件名、也不要凭 jar 名：

| 正文里出现 | 依赖谁 |
|---|---|
| `type: 'gtceu:sized'` 之类的 `type` 前缀 | GTCEu（原料类型由它注册） |
| `event.recipes.<命名空间>.<配方类型>(…)` | 那套 fluent builder 来自 GTCEu 的 KubeJS 插件——**即使配方类型是我们自己的 `nanochip_*`**，也仍然依赖 gtceu |
| `gtceu:*` 配方类型 | GTCEu |
| `kubejs:<id>` 物品 | 只是 KubeJS 注册的物品，不需要守卫 |
| `Java.loadClass('…')` | 那个类所在模组 |
| `global.XXX` 共享清单 | 不是模组依赖，是跨脚本约定，见第五节 |

## 三、守卫怎么写：两种，选一种，别混着来

- **包裹式**：`if (Platform.isLoaded('xxx')) { …整段注册… }`。适合一个文件只干一件事。参考 `instance/kubejs/server_scripts/pattern_assembly.recipes.js`。
- **回调内 early-return**：事件回调的第一行 `if (!Platform.isLoaded('xxx')) return`。适合一个回调里只有一段内容。参考 `instance/kubejs/server_scripts/recipe_conflicts.recipes.js`、`nac_processing.recipes.js`、`nac_restart.recipes.js`、`nac_matrix_tier.recipes.js`、`nac_persistence.recipes.js`、`nac_calibration_tiers.js` 这五个 gtceu 夹具。

要点：
- 守卫必须放在**回调内**、所有用到该模组的语句**之前**；回调外面的 `ServerEvents.highPriorityData(...)` 本身不用守。
- `Platform.isLoaded(id)` 的参数是 mods.toml 里的 modid，不是文件名。
- startup 与 server 两个阶段都能用；客户端脚本没验证过。

## 四、踩过的坑

- **只给一个脚本补守卫**。同一批脚本里 6 个写了 `gtceu:sized` / `event.recipes[product]`，只给其中 1 个加守卫，等于约定只落实了 1/6；下一个人照抄没加的那些，坑就回来了。
- **守卫守错主人**。物品登记脚本里可能混两类东西：一类只给上游模组的启动校验补料，另一类是**我们自己配方 JSON 里写死的原料**。用上游模组的 `isLoaded` 去守整段，等于给"上游以后被移出测试依赖"埋雷——物品不再注册，我们自己的配方解析失败（真踩过：`enhancedcore_ingredients.items.js` 里 3 件物品是我们 `conversion*` 配方的原料）。
- **这种失败不会 FAIL**。日志巡检只看本模组的 logger；KubeJS 的 `Failed to parse recipe … Unknown item` 是 WARN 且不归我们，现有用例也没有断言那些配方 id。表现只会是"少了几条配方"，没人会发现。**注册物品这件事宁可不守，也别守错。**
- **守卫分支可能从来没跑过**。某个模组在测试依赖表里永远启用时，守卫永远走 true 分支。防御性代码不是免责理由：至少要保证 false 分支不会裁掉别的东西。
- **跨脚本共享清单不要守卫**。件数这类清单只在 startup 单点定义、server 读 `global`，读不到就直接抛错——宁可测试服起不来，也不要静默少注册物品。
- **别信"夹具脚本只在测试服跑"**。它们确实不打进发行 jar，但复制一个文件到别的实例很常见，守卫是给这种复制留的余量。

## 五、两种注入方式，边界写清楚

| 方式 | 走哪条链 | 适用 |
|---|---|---|
| `ServerEvents.highPriorityData` + `event.addJson('<ns>:recipes/….json', {…})` | 直接注入**数据包**（早） | 需要完整控制 JSON 形状（`data` / `tickInputs` / `gtceu:sized`）的夹具 |
| `ServerEvents.recipes` + `event.recipes[product][type](id)` | 走 **GT/KubeJS 构建器**（晚） | 只想表达"输入→输出→时长/耗电"的夹具 |

当前两类没有 id 冲突（`calibration/*`、`nanochip/assembly_matrix/*` 与 `gtl_gametest:*` 分带）。**这是隐式约定**：一旦有人用构建器复用数据包侧的 id，"谁赢取决于执行顺序"。改夹具时保持 id 分带，不要交叉。

## 六、新增夹具模板

```js
ServerEvents.highPriorityData(event => {
    // 依赖 GTCEu：<为什么这条需要 GT>
    if (!Platform.isLoaded('gtceu')) return
    const product = Java.loadClass('com.gtlmodular.common.data.nanochip.NanochipModContext').modId()
    // <这条在测什么>
    event.addJson(product + ':recipes/…', { … })
})
```

物品侧同理，但只有在**确实缺那个模组就没人用**时才加守卫；我们自己配方要用的物品一律无条件注册。

## 七、两个已知噪音 / 边界（别当真回归查）

**1. 日志里成片的 `Failed to parse recipe … Unknown item 'kubejs:…'` 是预期的。**
完整版测试环境里，`src/main/resources/data/gtlmodular/recipes/nanochip/conversion*` 引用的那些 `kubejs:*`
原料是**整合包脚本**提供的，精简环境本来就没有；数量级约三百条，改动前后都在。判断口径只有一个：
**只看我们自己夹具脚本产出的 id 有没有少**（`gtl_gametest:*` 与 `kubejs:nac_*`、`kubejs:pattern_gate_*`）。
反例也要记住：`enhancedcore_ingredients.items.js` 里那 7 件必须真的注册上，否则 Enhancedcore 启动校验直接
`Missing equipment recipe ingredients` 把服务器拉不起来（已实测）。

**2. `global` 只在同一个游戏进程内跨阶段共享，不跨产品。**
`startup_scripts` → `server_scripts` 共享 `global` 是阶段保证（`nac_calibration.js` 定义件数表、`nac_calibration_tiers.recipes.js`
读取并做缺失即 `throw`）。但 `run-test`（完整版）与 `run-test-nac`（独立版）是**两套目录、两个进程**，
互不共享；所以两边都必须各自复制到 `startup_scripts/nac_calibration.js`（`prepare*GameTest` 对两者都会复制 `instance`）。
`full-instance` 只叠加给完整版，因此 `enhancedcore_ingredients.items.js` 在独立版环境里根本不存在——
它守的 `gtl_enhancedcore` 也只在完整版测试依赖里（见 [依赖.md](依赖.md) 的「仅完整版」行）。
