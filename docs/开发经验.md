# 开发经验

以前踩过的坑。每条按「现象 → 原因 → 以后怎么做」写。遇到相似的现象先来这里对一下。

## 查问题的顺序

1. 出问题前改过配置、换过 jar 的，先改回去试一次，再查代码。
2. 拿到玩家的 `latest.log` / `debug.log`，搜 `[gtlmodular`、`[gtl_nac`、`/swallowed]`、`Exception`。游戏里可以用 `/gtlmodular_nac errors`（独立版 `/gtl_nac errors`）看本次运行被捕获的异常。
3. 涉及上游（GTCEu、gtlcore、gtladditions、Enhancedcore）的行为，先 `gradlew.bat decompileDeps`，去 `deps-src/` 里看实际代码。不要凭印象，也不要信 GTNH wiki。
4. 要说「是某个版本改坏的」，先用 `git grep` 看旧版本标签里有没有同样的代码（例如 `git grep -n FORMED_SKIP v0.3.132`）。没对比过，就只能写「怀疑」。
5. 写一个能复现问题的 GameTest，先看到它 FAIL。
6. 修代码，看它变成 PASS，再把两套 GameTest 全跑一遍。
7. 复现不出来就说复现不出来，不要"凭感觉修一下"然后说修好了。

## 区块重载后模块连着旧主机（「时好时坏，重进才开工」）

- **现象**：NAC 有料、有电却不开工，退出重进又好了。
- **原因**：区块重新加载或读档后，同一个坐标上换成了新的主机对象。旧对象虽然已经失效（`isInValid()`），身上却还带着成形标记，它的延迟成形回调把模块又连回了自己。模块向一个已经不存在的主机报到，所以不干活。
- **以后**：保存别的机器的引用时，用之前确认它还是世界里的那台机器：`MetaMachine.getMachine(level, pos) == this`，并且没有 `isInValid()`。参考 `NanochipAssemblyComplexMachine.isLiveHost()`。`NacRestartTests` 是这个问题的回归测试。

## 读档后已成形，零件表却是空的（不加工）

- **现象**：读档后 NAC 主机或模块显示「结构已成型」和「结构部件尚未就绪」，有料也不加工。重进存档后换了一批机器卡住，看起来像重进也没用。
- **原因**：
  - `isFormed` 存档，零件表不存档。上游靠 `MultiblockState` 初始的 `UNINIT_ERROR` 在读档后重跑一次匹配，把零件表填回来。
  - 上游只在 `(offset + periodID) % 4 == 0` 的那一轮做这次匹配。`offset` 每次读档随机取。
  - `originalMode = false` 时，我们对已成形结构每 6 轮才放行 1 次。6 和 4 不互质，一半机器永远轮不到。
- **以后**：自己的节流叠在上游节流上面时，算一下两个周期，必须互质。`FORMED_SKIP` 要和 4 互质，用单元测试锁住。也不要从外部周期性重跑匹配，试过，会把结构判定搅乱。

## 输出满了丢产物

- **现象**：输出仓塞满时，原料和电都扣了，产物却没了。
- **原因**：gtlcore 的 `MultipleRecipesLogic.onRecipeFinish()` 不检查输出成功没有，直接清掉进度去找下一个配方。GTCEu 普通 `RecipeLogic` 大多数情况下也不检查。
- **以后**：上游忽略返回值的地方，我们自己要检查。NAC 先用 `NanochipRecipeOutputs.tryOutput()` 确认产物交付成功，失败就保持进度等待。规则是：输出满了就停下等，绝不丢产物。

## 合批时校准少记

- **现象**：组装矩阵合批加工，校准只涨了一份的量。
- **原因**：记账用的是耗电回调里的配方，那是还没按并行放大的原配方。
- **以后**：统计产量要在真正扣料成功之后、用已经放大并结算过概率的配方来算（`NanochipCalibrationInputMixin`）。

## 修好了，测试却说没修好

- **现象**：校准的修复明明是对的，GameTest 还是失败。
- **原因**：测试服根本没加载我们的 mixin。开发环境从源码目录启动，没有发行 jar 的 manifest，mixin 配置要单独传进去。
- **以后**：修复"没生效"时，先看 `mixin_application` 用例有没有通过，确认 mixin 真的注入了，再怀疑修复本身。

## 和别的模组的 mixin 冲突

- **现象 1**：新加的 mixin 一点作用都没有，日志里也没有报错。原因是 gtladditions 用 `@Overwrite` 重写了 `MultipleRecipesLogic.getRecipe`，我们同优先级的注入被整个跳过了。
- **现象 2**：0.3.138 的一个 mixin（优先级 1100）用 `@Redirect` 替换了 `getMaxParallel` 调用；而 Enhancedcore（优先级 1200）要在同一个调用上做 `@ModifyArg`，并且设了 `require=1`，找不到目标就崩溃。装了 Enhancedcore 的整合包很可能一启动就崩，所以 0.3.138 撤回了。
- **为什么测试没发现**：测试服装了 Enhancedcore，但它的 mixin 是 Java 21 字节码，开发环境的 Mixin 只支持到 Java 17，会悄悄跳过这些 mixin，只在 `debug.log` 里留一行 `Class version 65 required is higher than the class version supported`。
- **以后**：注入 gtlcore / GTCEu 的类之前，在 `deps-src/` 里搜一遍所有模组对同一个类、同一个方法的 mixin。我们的 mixin 统一用优先级 1300，排在它们后面。改完要在真实整合包里启动一次。

## 开发环境全过，正式环境一进存档就崩（方法名写错）

- **现象**：0.3.139 完整版在整合包里一进存档就崩，报 `Critical injection failure`。测试服两套 GameTest 全过。
- **原因**：
  - `remap = false` 的 mixin 不会被构建翻译，正式环境用的 `m_` 名字是手写的。
  - `IndependentCloneCommandMixin` 把 `saveWithoutMetadata` 的 `m_187482_` 写成了 `m_187480_`，那是另一个方法 `saveWithFullMetadata`。
  - 测试服用开发环境的名字，走的是另一个写法，所以测不出来。
- **以后**：手写 `m_` / `f_` 名字时，直接看正式环境的字节码核对。用 Gradle 缓存里的 `caches\forge_gradle\mcp_repo\net\minecraft\joined\1.20.1-*\joined-1.20.1-*-srg.jar`，对目标类执行 `javap -c -p`，看它实际调用的是哪个名字。改了 mixin 一定要在真实整合包里启动一次。

## 样板总成串配方

- **现象**：样板总成把一张样板的料喂给了别的配方表里的配方。
- **原因**：`PatternTypeGate` 把上游 `getProxyRecipes()` 的返回值当成 `Collection` 读，实际上它是 `Map<RecipeType<?>, List<GTRecipe>>`，类型对不上就走到了默认"放行"。
- **以后**：读上游的返回值，先去 `deps-src/` 确认真实类型。判断不了的时候默认拒绝，不要默认放行。

## 惰性样板总成不认编程电路

- **现象**：同一组原料、只是编程电路不同的两张样板，惰性总成认不出电路，配方被拒。
- **原因**：惰性总成不走上游的 `getRealPattern()`，槽位的电路缓存没有跟着样板更新。
- **以后**：区分配方时要把编程电路算进样板身份。改样板总成时三种总成（惰性、MV 熔融、超级）都要测，`PatternAssemblyTests` 覆盖了这三种。

## 能源仓装不下一份配方就永远等

- **现象**：模块只接自带的小能源仓，一份配方的耗电比仓容量还大，模块永远不开工。
- **原因**：规则是"开工前存够整批的电"，一份都存不下时没有出路。
- **以后**：写"等到条件满足"的逻辑时，想一下条件会不会永远满足不了。现在的规则：仓满就开工，逐 tick 扣电，断电时按 GT 的规则退进度。

## 电网供电卡在 ULV，或者要 Long.MAX EU/t

- **现象**：主机绑定电网后，模块要么"最大配方等级 ULV"找不到配方，要么要 9223372036854775807 EU/t。
- **原因**：GTCEu 只在结构成形那一刻算一次电压等级、缓存一次能源列表。成形可能发生在绑定电网之前（ULV），也可能发生在旧账户还在的时候（Long.MAX）。
- **以后**：绑定、解绑、放置之后都要重算。GTL 的电网是"有多少给多少"，每 tick 现扣，不预存，也不要给它加功率上限。之前加过一次上限，结果出现一批要跑 38400 秒的情况。

## 改了一个默认值，样板被吃了

`MoltenPatternAssemblyPartMachine.HAS_PATTERN_SLOT_ARCHIVE_FALLBACK` 改过一次默认值，结果出现了样板被吃掉的事故。已有的 `static final boolean` 默认值一律不改。

## Enhancedcore 的占位名

Enhancedcore 给没有中文译名的配方类型命名时，会写入「未命名加工模式」，并用这个字符串来识别占位名。我们的样板总成自动命名要把它当成"还没命名"。这个字符串一个字都不能改。

## 两个 jar 同时装

两个 jar 里有同包同名的类，同时装会冲突。拦截必须写在 `src/nacmod/resources/META-INF/mods.toml`：对 `gtlmodular` 声明一个版本范围永远不满足的可选依赖。写在模组构造器里就太晚了，那时类已经冲突了。

## 开发环境

- 开发环境的 Forge 版本要和整合包一致（现在是 47.4.16），不然依赖的模组可能加载不了。
- `gradlew.bat clean build` 写成一条会失败，分成两条执行。
- 换了 `libs/` 里的 jar，要删掉 `deps-src/` 里对应的目录，再 `decompileDeps`，不然看到的是旧源码。
