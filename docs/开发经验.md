# 开发经验

以前踩过的坑。每条按「现象 → 原因 → 以后怎么做」写。遇到相似的现象先来这里对一下。

## 查问题的顺序

1. 出问题前改过配置、换过 jar 的，先改回去试一次，再查代码。
2. 拿到玩家的 `latest.log` / `debug.log`，搜 `[gtlmodular`、`[gtl_nac`、`/swallowed]`、`Exception`。游戏里可以用 `/gtlmodular_nac errors`（独立版 `/gtl_nac errors`）看本次运行被捕获的异常。
3. 涉及上游（GTCEu、gtlcore、gtladditions、Enhancedcore）的行为，先 `gradlew.bat decompileDeps`，去 `deps-src/` 里看实际代码。不要凭印象，也不要信 GTNH wiki。要写「上游没有某个接口」「只有某几处会调它」之前，先搜一遍调用方（例如 `grep -rn addChangedListener deps-src/gtceu-*`），搜过才能这么写。
4. 要说「是某个版本改坏的」，先用 `git grep` 看旧版本标签里有没有同样的代码（例如 `git grep -n FORMED_SKIP v0.3.132`）。没对比过，就只能写「怀疑」。
5. 写一个能复现问题的 GameTest，先看到它 FAIL。**测试是在修复之后才写的，就把修复临时撤掉（`git stash` 或 `git revert --no-commit`）再跑一遍，必须看到它 FAIL。** 撤掉修复还 PASS，说明这个测试没测到问题，修复是不是对的也还没证明。
6. 修代码，看它变成 PASS，再把两套 GameTest 全跑一遍。
7. 复现不出来就说复现不出来，不要"凭感觉修一下"然后说修好了。
8. 玩家说「重进之后」才出的问题，**必须在同一个进程里真的重进一次**才复现得出来；只进一次是测不到的。
9. 拿测试里的日志当证据之前，先排除是测试自己造成的状态。例如夹具推料前故意暂停了宿主，那宿主「在睡觉」就是预期，不是故障。
10. 测试服测不到的场景（重进世界、真实整合包、别的模组的 mixin），提交说明里写明「还没在游戏里验证」，不要只写「GameTest 全绿」。

## 服务器线程卡住：先分清「卡住」还是「慢」

出现「客户端像卡死」「退世界一直停在保存世界」「ModernFix 看门狗报单 tick 超时」这类现象，
**先拿线程转储，不要凭印象改代码**。转储来源：ModernFix 看门狗超时自己会打；装了 spark 也可以 `/spark dump`。

1. **第一步：看两次转储是不是同一条栈。**
   - **同一条栈**、而且看门狗报的时长一直往上加（40001 → 81117 → 122815 …）⇒ **卡住**（死锁/自锁）。
     这说明这次 tick 根本没结束，别去查「为什么慢」。
   - 两次栈不一样、时长会回落 ⇒ **慢**（热点），这时才去查耗时。
2. **第二步：按包归属判责。** 数栈帧属于谁：我们（`com.gtlmodular`）、上游
   （GTCEu / gtlcore / gtladditions / LDLib）、还是别的模组。**一个我们的帧都没有，就别往自己身上揽。**
3. **第三步：能改就改，不能改就出报告。**
   - 定位到自己 ⇒ 换实现，**但匹配与玩法语义必须不变**。已有一例：结构预览的候选谓词直接用
     `Predicates.abilities(...)`，它内部是 `blocks(...)`，会**逐个实例化**该能力的所有方块；样板总成的
     构造是 O(槽位²)，一次能卡几十秒。换成「每种能力只实例化最便宜的一台」的廉价谓词后，匹配不变、卡顿消失。
   - 定位到别人 ⇒ 给上游写报告，按「现象 + 完整栈 + 复现步骤 + 归因证据」写，别只贴一句「卡了」。
4. **第四步：改完要能证明就是它。** 拿一个**不含本次改动**的旧 jar，在**同样的场景**下再复现一次；
   旧版一样出问题，才叫排除自己。只对比「旧 jar 没做这个操作、新 jar 做了」是不成立的。
## 区块重载后模块连着旧主机（「时好时坏，重进才开工」）

- **现象**：NAC 有料、有电却不开工，退出重进又好了。
- **原因**：区块重新加载或读档后，同一个坐标上换成了新的主机对象。旧对象虽然已经失效（`isInValid()`），身上却还带着成形标记，它的延迟成形回调把模块又连回了自己。模块向一个已经不存在的主机报到，所以不干活。
- **以后**：保存别的机器的引用时，用之前确认它还是世界里的那台机器：`MetaMachine.getMachine(level, pos) == this`，并且没有 `isInValid()`。参考 `NanochipAssemblyComplexMachine.isLiveHost()`。`NacRestartTests` 是这个问题的回归测试。

## 读档后已成形，零件表却是空的（不加工）

- **现象**：读档后 NAC 主机或模块显示「结构已成型」和「结构部件尚未就绪」，有料也不加工。重进存档后换了一批机器卡住，看起来像重进也没用。
- **原因**：
  - `isFormed` 存档，零件表不存档。上游靠 `MultiblockState` 初始的 `UNINIT_ERROR` 在读档后重跑一次匹配，把零件表填回来。
  - 上游只在 `(offset + periodID) % 4 == 0` 的那一轮做这次匹配。`offset` 每次读档随机取。
  - `originalMode = false` 时，我们对已成形结构每 6 轮才放行 1 次。6 和 4 不互质，一半机器永远轮不到。
- **以后**：自己的节流叠在上游节流上面时，算一下两个周期，必须互质。`FORMED_SKIP` 要和 4 互质，用单元测试锁住。也不要从外部周期性重跑匹配，试过，会把结构判定搅乱。

## 输出满了丢产物

- **现象**：输出仓塞满时，原料和电都扣了，产物却没了。
- **原因**：gtlcore 的 `MultipleRecipesLogic.onRecipeFinish()` 不检查输出成功没有，直接清掉进度去找下一个配方。GTCEu 普通 `RecipeLogic` 大多数情况下也不检查。
- **以后**：上游忽略返回值的地方，我们自己要检查。NAC 先用 `NanochipRecipeOutputs.tryOutput()` 确认产物交付成功，失败就保持进度等待。规则是：输出满了就停下等，绝不丢产物。

## 合批时校准少记

- **现象**：组装矩阵合批加工，校准只涨了一份的量。
- **原因**：记账用的是耗电回调里的配方，那是还没按并行放大的原配方。
- **以后**：统计产量要在真正扣料成功之后、用已经放大并结算过概率的配方来算（`NanochipCalibrationInputMixin`）。

## 修好了，测试却说没修好

- **现象**：校准的修复明明是对的，GameTest 还是失败。
- **原因**：测试服根本没加载我们的 mixin。开发环境从源码目录启动，没有发行 jar 的 manifest，mixin 配置要单独传进去。
- **以后**：修复"没生效"时，先看 `mixin_application` 用例有没有通过，确认 mixin 真的注入了，再怀疑修复本身。

## 和别的模组的 mixin 冲突

- **现象 1**：新加的 mixin 一点作用都没有，日志里也没有报错。原因是 gtladditions 用 `@Overwrite` 重写了 `MultipleRecipesLogic.getRecipe`，我们同优先级的注入被整个跳过了。
- **现象 2**：0.3.138 的一个 mixin（优先级 1100）用 `@Redirect` 替换了 `getMaxParallel` 调用；而 Enhancedcore（优先级 1200）要在同一个调用上做 `@ModifyArg`，并且设了 `require=1`，找不到目标就崩溃。装了 Enhancedcore 的整合包很可能一启动就崩，所以 0.3.138 撤回了。
- **为什么测试没发现**：测试服装了 Enhancedcore，但它的 mixin 是 Java 21 字节码，开发环境的 Mixin 只支持到 Java 17，会悄悄跳过这些 mixin，只在 `debug.log` 里留一行 `Class version 65 required is higher than the class version supported`。
- **以后**：注入 gtlcore / GTCEu 的类之前，在 `deps-src/` 里搜一遍所有模组对同一个类、同一个方法的 mixin。我们的 mixin 统一用优先级 1300，排在它们后面。改完要在真实整合包里启动一次。

## 开发环境全过，正式环境一进存档就崩（方法名写错）

- **现象**：0.3.139 完整版在整合包里一进存档就崩，报 `Critical injection failure`。测试服两套 GameTest 全过。
- **原因**：
  - `remap = false` 的 mixin 不会被构建翻译，正式环境用的 `m_` 名字是手写的。
  - `IndependentCloneCommandMixin` 把 `saveWithoutMetadata` 的 `m_187482_` 写成了 `m_187480_`，那是另一个方法 `saveWithFullMetadata`。
  - 测试服用开发环境的名字，走的是另一个写法，所以测不出来。
- **以后**：手写 `m_` / `f_` 名字时，直接看正式环境的字节码核对。用 Gradle 缓存里的 `caches\forge_gradle\mcp_repo\net\minecraft\joined\1.20.1-*\joined-1.20.1-*-srg.jar`，对目标类执行 `javap -c -p`，看它实际调用的是哪个名字。改了 mixin 一定要在真实整合包里启动一次。

## 样板总成串配方

- **现象**：样板总成把一张样板的料喂给了别的配方表里的配方。
- **原因**：`PatternTypeGate` 把上游 `getProxyRecipes()` 的返回值当成 `Collection` 读，实际上它是 `Map<RecipeType<?>, List<GTRecipe>>`，类型对不上就走到了默认"放行"。
- **以后**：读上游的返回值，先去 `deps-src/` 确认真实类型。判断不了的时候默认拒绝，不要默认放行。

## 惰性样板总成不认编程电路

- **现象**：同一组原料、只是编程电路不同的两张样板，惰性总成认不出电路，配方被拒。
- **原因**：惰性总成不走上游的 `getRealPattern()`，槽位的电路缓存没有跟着样板更新。
- **以后**：区分配方时要把编程电路算进样板身份。改样板总成时三种总成（惰性、MV 熔融、超级）都要测，`PatternAssemblyTests` 覆盖了这三种。

## 能源仓装不下一份配方就永远等

- **现象**：模块只接自带的小能源仓，一份配方的耗电比仓容量还大，模块永远不开工。
- **原因**：规则是"开工前存够整批的电"，一份都存不下时没有出路。
- **以后**：写"等到条件满足"的逻辑时，想一下条件会不会永远满足不了。现在的规则：仓满就开工，逐 tick 扣电，断电时按 GT 的规则退进度。

## 电网供电卡在 ULV，或者要 Long.MAX EU/t

- **现象**：主机绑定电网后，模块要么"最大配方等级 ULV"找不到配方，要么要 9223372036854775807 EU/t。
- **原因**：GTCEu 只在结构成形那一刻算一次电压等级、缓存一次能源列表。成形可能发生在绑定电网之前（ULV），也可能发生在旧账户还在的时候（Long.MAX）。
- **以后**：绑定、解绑、放置之后都要重算。GTL 的电网是"有多少给多少"，每 tick 现扣，不预存，也不要给它加功率上限。之前加过一次上限，结果出现一批要跑 38400 秒的情况。

## 改了一个默认值，样板被吃了

`MoltenPatternAssemblyPartMachine.HAS_PATTERN_SLOT_ARCHIVE_FALLBACK` 改过一次默认值，结果出现了样板被吃掉的事故。已有的 `static final boolean` 默认值一律不改。

## Enhancedcore 的占位名

Enhancedcore 给没有中文译名的配方类型命名时，会写入「未命名加工模式」，并用这个字符串来识别占位名。我们的样板总成自动命名要把它当成"还没命名"。这个字符串一个字都不能改。

## 两个 jar 同时装

两个 jar 里有同包同名的类，同时装会冲突。拦截必须写在 `src/nacmod/resources/META-INF/mods.toml`：对 `gtlmodular` 声明一个版本范围永远不满足的可选依赖。写在模组构造器里就太晚了，那时类已经冲突了。

## 开发环境

- 开发环境的 Forge 版本要和整合包一致（现在是 47.4.16），不然依赖的模组可能加载不了。
- `gradlew.bat clean build` 写成一条会失败，分成两条执行。
- 换了 `libs/` 里的 jar，要删掉 `deps-src/` 里对应的目录，再 `decompileDeps`，不然看到的是旧源码。

## 重进世界以后整个游戏卡死，退世界一直停在「保存世界」

- **现象**：同一个游戏进程里「退回标题 → 再进世界」，进去大约一分钟后整个游戏卡住，退世界永远停在「保存世界」，只能强杀进程。日志里 ModernFix 看门狗反复报**同一条** tick、时长一直涨（40001 → 333042 ms，每 41 秒加一次）。**只进一次世界不会出现。**
- **原因**：LDLib 的异步方块实体同步把发包任务交给 `Platform.getMinecraftServer().execute(...)`（`IAsyncAutoSyncBlockEntity.asyncTick`），任务只捕获了实体、没捕获服务器和 level。任务跨过世界重载执行时，它在**新服务器线程**上跑，却拿**旧 `ServerLevel`** 去 `getBlockState`；旧 `ServerChunkCache` 的 `mainThread` 是已经死掉的旧线程，于是这次调用被判成「非主线程」、走 `getChunkOffThread` 并 `join()` 一个只有那条死线程才能完成的加载 —— 服务器线程自锁，永远出不来。`AsyncThreadData.releaseExecutorService()` 只关线程池、**不清 `asyncLogics`**，也收不回已经进入服务器队列的任务。
- **这是 LDLib 的问题，不是我们的。** 用一个**不含相关改动的旧 jar**、同样「进 → 退 → 重进」复现过：**同样的栈，还更久**；只进一次的三次会话全部 0 次卡死。GTCEu 每个机器方块实体都实现了这个接口（`IMachineBlockEntity extends ... IAsyncAutoSyncBlockEntity`），而 `useAsyncThread()` 在上游没有任何覆盖，所以**所有机器**都走这条路，不限于 NAC。
- **以后**：
  - 本地兜底已经做了：`LDLibAsyncStaleLogicGuardMixin`（`3f2d12f`）在 `searchingTask` 分发 `asyncTick` 前，跳过属于已作废服务器、或属于别的 level 的条目。**截至 10-15 还没在游戏里验证过**：测试服不会「退回标题再进」，GameTest 全绿只能说明它装上了、没弄坏别的。
  - 上游报告照常提 lowdragmc/LDLib。提之前查清一点：LDLib 的 `CommonListeners` 在 `ServerStoppingEvent` 和 `LevelEvent.Unload` 时都会调 `releaseExecutorService()`，旧线程照理已经关了；旧名单还能接着跑，说明关掉之后又有东西调了 `addAsyncLogic` 把线程拉了起来。
  - 玩家侧：游戏里验证通过之前，切档仍然建议**直接重启游戏**，不要「退回标题再进」。
  - 排查时注意：卡住时的线程转储里 `LDLib Async Thread` **已经消失了**，别因为「看不到那个线程」就以为与它无关 —— 已经交给服务器队列的任务收不回来。

## 料推进去了，机器却「有配方但不动」

- **现象**：机器结构成型、配方存在、料也确实推进去了，但就是不开工；界面停在「未找到可运行的配方」；AE 那边的产物也一直不回来。**拆了重放、或者重进世界，立刻就恢复。**
- **原因：还没找到（截至 10-15）。** 已经确认的事实：
  - GTCEu 的机器会**休眠**。没有 tick 订阅时，`MetaMachine.serverTick()` 把方块状态 `server_tick` 置 `false`，`IMachineBlock` 只在它为 `true` 时返回 ticker，方块实体就不再被 tick。
  - **上游本来就有「来料叫醒宿主」这条链**，推料时会自动走：
    1. gtlcore `MEPatternBufferPartMachineBase.InternalSlot.pushPattern()` 末尾调 `onContentsChanged.run()`；
    2. `MEPatternBufferPartMachine` 在构造和 `onLoad()` 里把这个回调设成 `recipeHandler.getMeItemHandler().notifyListeners()`（流体同理）；
    3. GTCEu `WorkableMultiblockMachine.onStructureFormed()` 给每个零件的每个处理器挂了 `addChangedListener(recipeLogic::updateTickSubscription)`。

    所以「唤醒只有 `onMachineLoad()`、`setStatus()` 少数入口」「GTCEu 没有来料叫醒的接口」都不对。惰性总成的 `notifyMERecipeHandlers` 走的也是这条链，`wakeHostRecipeLogic` 只是反射失败时的退路。
  - `9495b13` 给熔融/超级总成加了推料后直接唤醒。对照实验（10-15）：把它撤掉，`PatternAssemblyTests` 的三条 `wake` 用例照样全 PASS。原因是用例只丢掉了 tick 订阅，没碰监听链，推料一通知宿主就醒了。所以**这个改动和用例都没触到游戏里的病根**。改动本身便宜、可重复调用，留着无害。
  - 怀疑方向（未证实）：料是在监听链断开的那段时间推进去的，比如结构复查、零件区块重载时 `onStructureInvalid()` 撤掉了监听；之后 AE 认为已经推过、不再推第二次，就没有任何变化能叫醒宿主。拆了重放会重新成形，`onStructureFormed()` 末尾会调一次 `updateTickSubscription()`，跟「拆了重放就好」对得上。
- **以后**：
  - 下次在游戏里遇到，**拆放之前先记下**：宿主 F3 的 `server_tick`；宿主是否成形、是否被暂停；日志里有没有 `推料时宿主控制器正处于休眠`；`/gtlmodular_nac errors` 的输出。
  - `server_tick` 是**方块状态**，不是「当前有没有在跑」。`false` = 这台机器已经被排除在 tick 之外。
  - 「机器不动」要分清是**配方算不出来**还是**机器没被 tick**：两者表象一样，但后者拆放一下就好，前者不会。
  - `9495b13` 的哨兵日志可以当探针，但要排除宿主被暂停（`isWorkingEnabled() == false`）的情况。现有夹具推料前会故意暂停宿主，不排除就会误报：「测试里报了 6 次」就是这么来的。
  - 找到真病因后，回归用例要按「查问题的顺序」第 5 条，确认撤掉修复时它会 FAIL。
