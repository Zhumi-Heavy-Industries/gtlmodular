## 5. 根因证据（不要重新推一遍）

**① 拆块不失效**——上游 `MultiblockControllerMachine.asyncCheckPattern`（`deps-src/gtceu-1.20.1-1.4.4/.../MultiblockControllerMachine.java:135`）**只在"异步检查成形"这条路上**调 `mwsd.addMapping(state)`；而"方块变化 → `MultiblockState.onBlockStateChanged` → `checkPatternWithLock` → `onStructureFormed`"这条路（同文件 `MultiblockState.java:157-186`）**不登记**。没登记 = 该控制器不在 `chunkPosMapping` 里 = 之后结构内任何一格被拆，世界数据都不会通知它。修复就是成形后补同一句 `addMapping`（幂等，`mapping` 以控制器坐标为键）。

**② AE 第二单卡住**——我们自己 2026-10-25 的取证已经给出结论，见工作区：
- `_census\连接机制改造_实施记录.md` §9.3：「控制器那张『配方 → 槽』缓存 `recipes2SlotsMap` 的唯一重建口是 `upDate()`，只由结构成形/镜像重绑触发；读档与区块重载之后没人重建」；星律（山海）的解法是样板总成 `onLoad` 里延迟 1/20 tick 做 `upDate()` + `restoreMachineCache` + `updateTickSubscription`。
- `_census\NAC合成链路_原初对照与重构方案.md` ④：「第一次 job 把系统推到『AE 备了料、机器没消费』那一格后不会自愈 ⇒ 第二次必然跑不动」。
- gtlcore 侧实现：`MEPatternRecipeHandlePart.restoreMachineCache(BiConsumer<GTRecipe, IRecipeHandlePart>)`（`deps-src/gtlcore-1.2.3.2-fix4/.../MEPatternRecipeHandlePart.java:62-83`）、`IRecipeCapabilityMachine.tryAddAndActiveRhp`（`:50`）。

**③ JEI 预览串页**——从玩家截图可算：预览页底部方块计数 2226+32+287+3728+1243+53 = **7569**，正好等于主机 `MultiblockState.cache` 的格数（当天日志同一台机 `cache 实测=7569`）。即"查矩阵物品时打开的其实是复合体那一页"。注册处源码与 jar 都确认是分开的（主机 `.pattern(NanochipComplexPattern::build)`、模块 `.pattern(NanochipComplexPattern::buildModule)`），所以不是在注册处串的；需要启动那行 `NAC 预览格数` 来二分：矩阵那行若是 7569 ⇒ 运行时 definition 串了；若是一两百 ⇒ 是 JEI catalyst 映射串了。
