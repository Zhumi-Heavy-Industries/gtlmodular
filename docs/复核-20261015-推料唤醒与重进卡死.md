## 三、推料唤醒：为什么说没触到病根

### 1. 上游本来就会在推料时叫醒宿主

- gtlcore `MEPatternBufferPartMachineBase.InternalSlot.pushPattern(KeyCounter[])` 末尾调 `this.onContentsChanged.run()`。
- `MEPatternBufferPartMachine` 在构造函数和 `onLoad()` 里把每个内部槽的回调设成 `recipeHandler.getMeItemHandler().notifyListeners()` 和 `getMeFluidHandler().notifyListeners()`。
- GTCEu `WorkableMultiblockMachine.onStructureFormed()`（`deps-src/gtceu-1.20.1-1.4.4/.../WorkableMultiblockMachine.java` 第 110 行）给每个零件的每个处理器挂了 `handler.addChangedListener(this.recipeLogic::updateTickSubscription)`。
- 熔融总成没有覆盖 `createInternalSlot`，`onLoad()` 也调了 `super.onLoad()`，所以这条链是完整的。

所以文档里这两句不对：「唤醒只有 `onMachineLoad()`、`setStatus()` 等少数入口」，以及「GTCEu 全库没有来料叫醒的接口」。惰性总成的 `notifyMERecipeHandlers` 走的也是这条链，`wakeHostRecipeLogic` 只是反射失败时的退路。所以它不能证明「推料方必须自己唤醒」。

### 2. 用例为什么抓不到

`breakHostTickSubscription()` 只丢掉了 tick 订阅，没碰处理器上的监听。推料一通知，`updateTickSubscription()` 就把宿主叫醒了。有没有 `9495b13` 结果都一样。

### 3. 「哨兵在测试里报了 6 次」不是证据

老的样板总成用例在推料前会 `setWorkingEnabled(false)`，宿主是**被故意暂停**的，睡着是预期。哨兵在这种状态下当然会报。

### 4. 建议

- `9495b13` 可以留，它便宜，也可以重复调用。但请改两处：
  - 哨兵加一个条件：宿主被暂停（`isWorkingEnabled() == false`）时不报。这样游戏里一旦出现这行，才说明「宿主没暂停、料推进去了还在睡」，也就是监听链真的断了。这行日志就成了抓真病因的探针。
  - 提交说明和文档不要再说它修好了「有配方但不动」。文档我已经改成「原因未找到」。
- `de0427d` 的 `wake` 用例可以留着，当作「唤醒链正常」的覆盖。把注释里「能抓住宿主休眠没人唤醒」改掉。
- 真病因怎么查：下次在游戏里遇到，**拆放之前**先记下这几样：
  - 宿主 F3 的 `server_tick`；
  - 宿主是否成形、是否被暂停；
  - 日志里有没有哨兵那一行；
  - `/gtlmodular_nac errors` 的输出。

  有个怀疑方向（未证实），写在 [开发经验.md](开发经验.md) 里了。

- 名单属于已作废的服务器，整条跳过；

- 同一 level 的正常实体不受影响。

GameTest 只能证明 mixin 装上了、没弄坏别的，证明不了卡死治好了，因为测试服不会「退回标题再进」。收之前还要做三件事：

1. **在真实整合包里启动一次。** 这是 AGENTS.md 对新 mixin 的规矩。
2. **按你们复现时的做法验一遍：** 同一进程里「进 → 退回标题 → 再进」，进去等 3 分钟以上再退出，重复 3 次。
3. **建议给守卫加一条限频日志。** 跳过时记一次，比如「跳过上一局的异步同步 N 条」。这样验证时能看到它确实出过手，而不只是「这次碰巧没卡」。

另外有一点没解释清，不影响收。LDLib 的 `CommonListeners` 在 `ServerStoppingEvent` 和 `LevelEvent.Unload` 时都会调 `releaseExecutorService()`，旧线程照理已经关了。旧名单还能接着跑，说明关掉之后又有东西调了 `addAsyncLogic`，把线程重新拉了起来。给 LDLib 写报告前把这点查清，报告会更站得住。

## 六、下次写修复和测试时

这次的问题不在代码写得不好，在**证据不够就下了结论**。这几条已经写进 [开发经验.md](开发经验.md) 的「查问题的顺序」：

1. **回归用例必须见过 FAIL。** 用例写在修复之后的，把修复临时撤掉（`git stash` 或 `git revert --no-commit`）跑一遍，看到 FAIL，再恢复修复看它 PASS。撤掉修复还 PASS 的用例，什么也没证明。这次要是做了这一步，当场就会发现 `9495b13` 没碰到病根。
2. **拿测试日志当证据之前，先排除是测试自己造成的状态。**
3. **写「上游没有某个接口」之前，先搜一遍调用方。** `grep -rn addChangedListener deps-src/gtceu-*` 一行就能看到。
4. **测试服测不到的场景，提交说明里写明「还没在游戏里验证」。** 这类场景包括重进世界、真实整合包、别的模组的 mixin。不要只写「两套 GameTest 全绿」。
